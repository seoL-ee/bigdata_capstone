# 보호동물 장기 생활 적합성 추천 시스템 설계 초안

> 문서 상태: 시스템 설계 초안
> 기준 시점: 2026-10-03
> 범위: 기존 기획·논문·데이터 조사와 RescueGroups 전체 snapshot 실증 결과를 통합한 설계. 모델과 추출 target의 최종 확정은 포함하지 않는다.

## 문서의 판단 표기

이 문서는 근거의 종류를 다음과 같이 구분한다.

- **[기존 근거]** 기존 프로젝트 문서 또는 검토한 논문에서 직접 확인한 내용
- **[실데이터 확인]** 현재 저장소의 RescueGroups 전체 snapshot 및 산출물에서 확인한 내용
- **[설계 결정]** 위 근거를 종합해 이 문서에서 채택한 시스템 구조
- **[설계 가정]** 구현 방향을 구체화하기 위해 두었지만 아직 데이터나 논문으로 충분히 검증되지 않은 내용
- **[추가 검증]** 다음 단계의 데이터 분석이나 실험 없이는 확정할 수 없는 내용

핵심 결론은 다음과 같다. 이 시스템의 목적은 사용자가 선호할 동물을 맞히는 것이 아니라, **사용자·가구의 조건과 동물의 복지 요구가 장기적으로 함께 유지될 가능성을 검토하도록 돕는 것**이다. 그러나 현재 장기 적합성의 정답 데이터는 없다. 따라서 MVP는 장기 성공확률을 예측하지 않고, 객관적 조건으로 후보를 좁힌 뒤 확인된 적합성, 근거의 충분성, 결정에 중요한 미확인 정보를 분리해 제시하는 의사결정 지원 시스템으로 설계한다.

## 1. 현재까지 확정된 프로젝트 방향

### 1.1 문제 정의

**[설계 결정]** 프로젝트의 문제를 다음과 같이 정의한다.

> 불완전하고 보호소별 편차가 큰 보호동물 정보에서, 사용자 선호와 가구의 양육 가능성, 동물의 복지·생활 요구를 구분해 비교하고, 중요한 미확인 정보를 부적합으로 처리하지 않은 채 확인 행동을 제안하여 추천을 갱신하는 입양 의사결정 지원 문제

이 정의는 기존 기획의 “가구 생활환경 기반 장기 적합성” 방향과 일치한다. 또한 입양 선택과 장기 유지가 같은 outcome이 아니고, 반환·실패가 동물 행동만이 아니라 기대, 주거, 시간, 비용, 기존 동물 등과 연결된다는 01·03 논문 분석과도 일치한다. 동물 관점은 데이팅형 reciprocal preference가 아니라 **관찰 가능한 복지·안전·돌봄 요구가 해당 가구에서 충족될 수 있는지**로 표현한다.

### 1.2 현재 확정할 수 있는 것과 없는 것

| 구분 | 현재 판단 | 근거 상태 |
|---|---|---|
| 전국 후보의 객관적 기본정보 확보 | 국가동물보호정보 API를 중심으로 가능 | 기존 API 실증 완료 |
| 한국 실제 추천 대상과 상세 서술 확보 | PawInHand를 실제 추천 catalog와 한국어 evidence의 주요 원천으로 사용 | 기존 수집·기획 근거. 최신 범위·연결률은 별도 확인 필요 |
| RescueGroups 수집 가능 규모 | Dogs 31,622, Cats 30,968 unique, 합계 62,590개 확보 | 실데이터 확인 완료 |
| RescueGroups 원본과 분석 포맷 | raw JSON과 종별 Parquet 확보 | 실데이터 확인 완료 |
| RescueGroups 전량 attribute coverage | 계산 완료 | 실데이터 확인 완료 |
| description과 structured target의 실제 overlap | 미확정 | 추가 검증 필요 |
| structured target의 label 신뢰도와 클래스 불균형 영향 | 미확정 | 추가 검증 필요 |
| 영어권 RescueGroups에서 한국어 PawInHand로의 전이 성능 | 미확정 | 수작업 한국어 검증셋 필요 |
| 장기 입양 성공확률 | 현재 예측하지 않음 | 연결된 장기 outcome ground truth 없음 |
| CF·A-LLMRec | MVP에서 제외 | 반복 user–animal interaction 부족 |
| 학습형 AFA·통계적 reject | 효과 주장 보류 | target, 획득비용, 보류 사례의 독립 정답 부족 |

### 1.3 시스템의 기본 원칙

1. `Unknown`을 `No`, 0점, 평균적 성격으로 바꾸지 않는다.
2. 사용자 선호, 가구의 양육 가능성, 동물의 복지·안전 요구를 한 개념으로 합치지 않는다.
3. 행동·성격, household compatibility, care burden, objective information을 별도 feature family로 유지한다.
4. 동물 행동값에는 가능한 범위에서 출처, 원문, 관찰 맥락, 시점, 추출 방식을 함께 보존한다.
5. Match Score와 Evidence Coverage를 분리한다. 정보가 많다는 이유로 높은 순위를 주지 않는다.
6. 미확인 안전·공존 정보는 자동 hard negative가 아니라 확인 또는 담당자 검토의 근거가 된다.
7. LLM은 텍스트 구조화·근거문장 추출·설명 문구 생성에 제한적으로 사용하고, 없는 사실 생성이나 최종 적격 판정을 맡기지 않는다.
8. 입양 완료, 클릭, 문의, 만족, 반환, 장기 유지, 동물복지를 서로 다른 outcome으로 평가한다.

## 2. 기존 연구에서 도출된 설계 근거

### 2.1 입양 의사결정과 사용자

**[기존 근거]** 01 논문 분석에서는 외모·나이·크기 같은 선호와 함께 행동, 건강, 가족·기존 동물, 주거·생활양식, 비용·돌봄 부담, 과거 양육 경험, 직원 설명과 직접 상호작용이 입양 선택 또는 만족과 관련된 변수로 반복된다. 다만 선호를 맞힌 것이 장기 적합성의 정답은 아니다.

**[설계 결정]** 사용자 입력을 “좋아하는 동물”만 묻는 선호 설문으로 구성하지 않는다. 기존 동물·아동·주거 제한·외출시간처럼 부적합 시 피해가 큰 조건, 실제 제공 가능한 돌봄, 낮은 위험의 취향을 구분한다. 처음부터 긴 설문을 강제하지 않고 후보군과 critical unknown에 따라 추가 질문을 획득한다.

### 2.2 행동과 성격의 측정

**[기존 근거]** 02 논문 분석은 행동 construct가 측정 가능하지만 종, 관찰 상황, 시점, 평가자, 실제 상황 노출 여부에 따라 값과 의미가 달라짐을 보여준다. 보호소 단회 관찰이 입양 후 행동을 모든 항목에서 안정적으로 예측하지 못했고, 품종은 개별 행동의 강한 proxy가 아니다. 개와 고양이의 construct도 동일하지 않다.

**[설계 결정]** 행동 feature를 영구적 성격값으로 저장하지 않는다. 예를 들어 `fearfulness`는 값만 두지 않고 `source`, `observation_context`, `observed_at`, `evidence_text`, `value_state`를 함께 보존한다. 품종 평균으로 결측 행동을 채우지 않는다. 개·고양이 공통 축은 최소화하고 종별 schema를 둔다.

### 2.3 입양 실패, 반환, Foster

**[기존 근거]** 03 논문 분석은 단기 반환, 장기 owner surrender, foster 종료, 입양 전환, 반환 후 재입양이 서로 다른 outcome임을 확인했다. 반환 사유에는 행동뿐 아니라 기대 불일치, 기존 동물과의 갈등, 주거·시간·비용이 함께 나타난다. Foster는 복지와 추가 관찰의 잠재적 원천이지만 추천 정확도나 반환 감소를 자동으로 보장하지 않는다.

**[설계 결정]** “반환 위험 점수” 하나를 추천 목표로 삼지 않는다. Foster 기록은 있을 경우 높은 가치의 evidence source로 취급하되, 그 자체를 ground truth로 간주하지 않는다. 기존 동물과 새 동물의 관계는 한 방향의 `dog_sociability`가 아니라 가구 조건과 `dogs_compatible` evidence를 함께 확인한다.

### 2.4 추천기술과 불확실성

**[기존 근거]** 05 통합분석에서 RRS·multistakeholder, MNAR/DR, reject option, AFA, A-LLMRec, Agent는 서로 다른 문제층을 다룬다. 반복 interaction, propensity, 독립 label, feature 획득비용이 없으면 원 논문 수준의 기술 적용이나 성능 주장을 할 수 없다.

**[설계 결정]** 설명 가능한 weighted content-based scoring은 삭제하지 않고 MVP 기준선으로 유지한다. Final 추천 구조는 단순 CBF가 아니라 **Constraint-based + Multi-Criteria + Evidence/Uncertainty-aware Recommendation**으로 정의한다. 확인된 hard·welfare 조건은 낮은 우선순위의 선호 점수로 상쇄할 수 없고, 불확실성은 별도 evidence 계층, 점수·순위 구간과 상태 전이로 처리한다. LLM reranking이나 Agent orchestration은 baseline 대비 명확한 증분 가치가 정의될 때만 Final 후보가 된다.

### 2.5 기존 자료와 최신 RescueGroups 실증의 관계

기존 해외데이터 문서의 “RescueGroups API 승인 후 규모·coverage 확인”은 완료되었다. 현재 snapshot은 다음을 보여준다.

- **[실데이터 확인]** Dogs 31,622 unique, Cats 30,968 unique, 총 62,590개다.
- **[실데이터 확인]** `descriptionText` coverage는 Dogs 67.00%, Cats 71.23%다.
- **[실데이터 확인]** `activityLevel`은 23.33%/20.84%, `energyLevel`은 21.80%/16.95%, `exerciseNeeds`는 19.81%/13.07%다.
- **[실데이터 확인]** `isDogsOk`는 44.50%/20.33%, `isCatsOk`는 22.46%/49.56%, `isKidsOk`는 33.31%/29.19%다.
- **[실데이터 확인]** `isHousetrained`는 32.29%/54.15%, `newPeopleReaction`은 24.85%/24.47%, `ownerExperience`는 14.15%/11.48%다.
- **[실데이터 확인]** 여러 필드에서 비결측 값 중 한 범주의 비중이 70~99%에 이른다. coverage만으로 유용한 학습 target이라고 판단할 수 없다.

따라서 RescueGroups를 “핵심 학습 데이터”라고 확정하는 기존 표현은 다음처럼 수정한다.

> RescueGroups는 텍스트와 일부 structured attribute가 함께 있는 대규모 **학습·검증 후보 데이터**다. 실제 target 채택은 description–label overlap, label 의미, 종별 클래스 분포, 기관별 기록편향, 중복·누수 가능성을 확인한 뒤 결정한다.

## 4. 전체 시스템 architecture

```text
[국가동물보호정보 API] ─┐
                         ├─> Identity Resolution ─> Base Animal Profile
[PawInHand catalog/text] ─┘                              │
                                                        ├─> Evidence Store
[RescueGroups text + structured attributes]             │    - source
                │                                       │    - context/time
                └─> Feature Extraction 후보 개발 ───────┘    - original span
                                                             - value state
[C-BARQ / Shelter C-BARQ / Feline] ─> Species Taxonomy ──────┘

[User onboarding]
  └─> Household constraints + Care capacity + Preferences
                      │
                      v
              Hard constraint filtering
                      │
                      v
                Candidate animals
                      │
                      v
        Feature-wise compatibility by decision family
                      │
        ┌─────────────┼─────────────┐
        v             v             v
 Multi-criteria   Evidence/      Non-compensatory
   ranking       uncertainty      welfare check
        └─────────────┼─────────────┘
                      v
         Critical Unknown / Safety review
                      │
           ┌──────────┼──────────┐
           v          v          v
       Ready      Needs info   Team review / Hold
           │          │          │
           └────> Top-K + 이유 + 미확인 항목
                         + 보호소 질문/관찰 행동
                              │
                              v
                  새 Evidence 입력 후 재추천
```

### 4.1 주요 컴포넌트

1. **Catalog layer**: 국가 API와 PawInHand 개체를 가능한 범위에서 연결하고 실제 추천 가능한 상태를 관리한다.
2. **Profile layer**: 사용자와 동물의 정보를 서로 다른 schema로 구조화한다.
3. **Evidence layer**: 구조화 값보다 한 단계 아래에서 출처·시점·맥락·원문·추출 방법을 보존한다.
4. **Eligibility layer**: 확인된 hard constraint 위반만 제외하고, unknown은 verification으로 보낸다.
5. **Scoring layer**: feature별 compatibility function으로 선호, care capacity, welfare requirement, household compatibility를 분리 계산하고 multi-criteria ranking을 수행한다.
6. **Uncertainty layer**: unknown을 0이나 평균으로 대체하지 않고 정보량, 출처 품질, 충돌, 사용자별 중요도를 바탕으로 score/rank uncertainty, 상태와 추가 확인 항목을 만든다.
7. **Presentation layer**: Top-K, 추천 이유, 불확실성, 질문, 원문 근거를 함께 제시한다.
8. **Feedback layer**: 보호소 답변·Meet·산책·Foster 등 새 evidence를 기존 기록을 덮어쓰지 않고 추가한다.

## 5. User Profile

### 5.1 질문 설계 원칙

**[설계 결정]** 질문은 추천 의사결정에 쓰이는 변수만 수집한다. 각 질문은 `constraint`, `care_capacity`, `preference`, `context` 중 하나의 목적을 가져야 한다. 근거가 약하거나 추천 결과에 사용하지 않는 질문은 넣지 않는다.

### 5.2 초기 필수 질문

| 영역 | 질문/필드 | 사용 목적 | 기본 처리 |
|---|---|---|---|
| 대상 범위 | 희망 종 | 후보군 결정 | hard filter |
| 지역·이동 | 거주지역, 이동 가능한 거리 | 방문·입양 가능한 후보군 | hard 또는 운영 제약 |
| 주거 제한 | 임대·관리규약의 종/크기/마릿수 제한 | 법적·계약상 불가 후보 제외 | 확인된 경우 hard |
| 가구 구성 | 성인·아동 유무와 아동 연령대 | 안전·공존 정보의 중요도 결정 | compatibility unknown 시 verification |
| 기존 동물 | 개·고양이·기타 동물의 유무와 수 | 공존 정보의 중요도 결정 | compatibility unknown 시 verification |
| 부재 시간 | 평일 일반 외출시간과 돌봄 공백 | 분리 관련 요구·배변·운동 capacity | soft 또는 verification |
| 활동 제공 | 일일 산책·놀이 가능시간, 체력 수준 | 활동·운동 요구 비교 | soft, 극단적 충돌은 warning |
| 경험 | 개/고양이 양육 경험과 행동관리 경험 | `experienced_owner_required` 비교 | 확인된 필수요건은 hard/verification |
| 돌봄 능력 | 투약·정기치료·특별관리 가능 여부 | health/special needs 비교 | 사용자가 불가 + 확인된 필수관리면 hard |
| 감당 제한 | 소음, 털관리, 배변훈련, 대형동물 등 절대 불가 항목 | 개인별 hard/soft 경계 설정 | 사용자가 명시한 절대 불가는 hard 후보 |

### 5.3 초기 선택 질문

- 나이·크기·성별·외형 선호
- 활동성과 애정 표현 수준의 선호
- 초보 보호자로서 원하는 훈련·생활관리 난도
- 특별돌봄 동물을 적극 고려할 의향
- 입양 시기와 방문 가능 시간

이 항목은 기본적으로 soft preference다. 외형·품종 선호가 행동 추정이나 동물의 가치 판단으로 전환되지 않게 한다.

### 5.4 추천 과정에서 추가로 묻는 질문

후보군의 정보와 현재 순위가 정해진 뒤에만 질문한다.

- 상위 후보의 `cats_compatible`가 unknown이고 기존 고양이가 있을 때, 합사 절차와 분리공간 제공 가능 여부
- `separation_related`가 unknown이고 장시간 외출할 때, 초기 적응기간의 임시 돌봄 또는 일정 조정 가능 여부
- 활동 요구가 경계선일 때 주말과 평일의 실제 활동 제공 차이
- special care 상세가 있을 때 구체적인 투약·내원 빈도를 감당할 수 있는지
- 두 후보의 순위를 실제로 바꾸는 사용자의 선호 우선순위

**[설계 결정]** MVP에서는 Critical Unknown을 탐지해 추가 확인 필요를 표시하고, 사용자가 선택한 질문·관찰로 새 evidence를 입력하면 추천 pipeline을 다시 실행한다. 어떤 unknown을 먼저 확인할지는 자동 최적화하지 않는다.

**[설계 가정]** Final/P1에서는 규칙 기반 decision sensitivity로 각 unknown을 확인했을 때 줄어드는 rank uncertainty와 recommendation-state uncertainty를 추정한다. 가능한 순위 범위, 상태 전이 가능성, 확인 비용·안전성·획득 가능성을 함께 비교해 불확실성을 가장 크게 줄이는 질문을 우선한다. 학습형 AFA나 VOI라는 명칭과 효과 주장은 target과 비용 데이터가 마련되기 전에는 사용하지 않는다.

이 추가 질문은 불확실성 처리와 분리된 부가기능이 아니라 다음 closed-loop의 일부다.

```text
현재 User Profile + Animal Evidence
                ↓
        Critical Unknown 탐지
                ↓
 P0: 추가 확인 필요 표시 / P1: rank·state uncertainty 감소 비교
                ↓
 사용자 질문 / 보호소 질문 / 관찰 제안
                ↓
             새 Evidence
                ↓
 User Profile 또는 Animal Profile 갱신
                ↓
          Recommendation 재계산
```

P0 구현은 unknown 탐지, 확인 필요 표시, evidence update와 pipeline 재실행까지 지원한다. P1 dynamic questioning은 여러 unknown 중 어떤 질문이 상태나 순위 불확실성을 가장 크게 줄이는지 비교한다. 어느 단계에서도 단순히 정보가 비어 있다는 이유만으로 모든 질문을 요구하지 않는다.

## 6. Animal Profile

**[설계 결정]** 이 절의 Animal Profile은 MVP에서 전부 자동 구현하기로 확정한 최소 schema가 아니라, 문헌·프로젝트 조사와 현재 데이터에서 도출한 **canonical candidate schema**다. 범위가 넓다는 이유로 feature를 먼저 삭제하지 않는다. 후속 데이터 검증에서 각 feature를 `direct`, `ML extraction`, `LLM extraction`, `verification-only`, `unsupported` 중 하나 이상으로 routing하고, 근거가 충분하지 않은 feature는 추천 점수에 강제로 사용하지 않는다. routing 상태는 데이터와 평가 결과가 추가되면 변경할 수 있다.

### 6.1 Profile의 네 계층

| 계층 | 의미 | 예시 |
|---|---|---|
| Objective / Basic | 관찰자 해석이 적은 기본정보 | species, age_group, sex, weight, size, neuter, location, shelter, availability |
| Behavior / Personality | 상황에서 보인 행동 경향 | fearfulness, human_sociability, activity, stranger_reaction, touch_sensitivity |
| Household Compatibility | 특정 가구 구성원과 함께 생활 가능한지에 대한 evidence | dogs_compatible, cats_compatible, children_compatible |
| Care Burden / Requirements | 지속적으로 필요한 시간·기술·비용·환경 | exercise_need, grooming_need, vocality, housetraining, special_care, experienced_owner_required |

`isDogsOk`와 `dog_sociability`는 합치지 않는다. 전자는 생활 가능성에 대한 직접·간접 판정이고, 후자는 다른 개를 향한 행동 성향이다. `activity_level`과 `exercise_need`도 각각 관찰된 활동성과 필요한 돌봄량이므로 구분한다.

### 6.5 Evidence record

각 structured value는 가능한 경우 아래 evidence와 연결한다.

```yaml
feature: cats_compatible
value_state: yes | no | unknown | conditional | conflicting
value: true | false | category | null
source_type: api_structured | shelter_text | staff | previous_owner | foster | meet | direct_observation | model
source_id: 원본 레코드 또는 문서 식별자
evidence_text: 원문 근거 문장 또는 null
observation_context: shelter | foster_home | previous_home | meet | walk | unknown
observed_at: 날짜 또는 null
recorded_at: 날짜
extractor: source_native | rule | llm | human
extraction_confidence: 선택적 수치 또는 등급
review_status: unreviewed | human_verified | disputed
```

`extraction_confidence`는 사실의 참확률과 동일하지 않다. 원문이 명확하게 추출되었어도 관찰 상황이 제한적일 수 있다. 따라서 추출 확신도, 출처 품질, 관찰 범위는 분리한다.

### 6.6 Feature implementation routing

canonical feature마다 구현 경로를 명시한다. 하나의 feature가 데이터 source나 종에 따라 서로 다른 route를 가질 수 있으며, 최종 route는 후속 feasibility와 gold set 평가로 확정한다.

| 상태 | 의미 | 추천 사용 조건 |
|---|---|---|
| `direct` | 구조화되어 있고 의미와 결측 처리를 신뢰할 수 있는 source에서 직접 사용 | source·갱신시점·값 정의가 확인되어야 함 |
| `ML extraction` | 충분한 학습 label과 독립 평가셋이 있을 때 모델로 텍스트에서 추출 | feature별 성능·abstention·도메인 전이 평가를 통과해야 함 |
| `LLM extraction` | LLM으로 구조화하되 명시적 원문 evidence를 필수로 요구 | 원문 span, 허용 label, abstention을 강제하고 unsupported claim을 평가해야 함 |
| `verification-only` | 자동 추론보다 보호소 질문, Meet, 산책, 관찰 등 추가 확인으로 처리 | 확인 전에는 `unknown`을 유지하고 필요 시 상태를 `Needs information` 또는 `Team review`로 둠 |
| `unsupported` | 현재 데이터와 근거로 시스템 판단에 사용하지 않음 | 화면 참고정보로도 오해 가능성이 있으면 노출하지 않음 |

`unsupported`는 canonical schema에서 feature를 삭제한다는 뜻이 아니다. 현재 버전에서 사용하지 않는다는 상태이며, 새로운 source·label·평가 결과가 생기면 다시 routing한다.

## 7. Hard / Soft / Unknown 처리

### 7.1 판정 원칙

| 유형 | 정의 | 예시 | Unknown일 때 |
|---|---|---|---|
| Hard constraint | 위반이 확인되면 후보로 제시할 수 없거나 사용자·동물에게 중대한 위험이 있는 조건 | 종/지역 범위, 계약상 크기 제한, 사용자가 절대 불가한 필수 의료관리, 보호소의 공식 입양 제한 | 제외하지 않고 정보 확인 또는 담당자 검토. 단, 확인 전 `Ready`로 표시하지 않을 수 있음 |
| Soft preference | 만족도가 달라질 수 있으나 협의·적응 가능한 조건 | 나이·성별 선호, 활동성 선호, 털관리 선호 | 점수에 넣지 않거나 neutral 처리. coverage는 낮아짐 |
| Warning / verification | 중요하지만 현재 값이 없거나 단회 관찰로 확정하기 어려운 조건 | 기존 고양이 가구의 `cats_compatible`, 어린이 가구의 접촉 안전, 장시간 외출의 separation 정보 | 중요도에 따라 `Needs information` 또는 `Team review` |

### 7.2 Hard constraint 후보의 세분화

1. **시스템 hard**: 추천 catalog 밖, 입양 불가 상태, 거리·종 범위처럼 사실관계가 명확한 항목
2. **사용자 선언 hard**: 사용자가 명시적으로 절대 불가라고 답한 조건
3. **기관 hard**: 보호소가 공식적으로 정한 입양 제한. 출처와 최신성을 표시
4. **안전 review gate**: 자동 제외가 아니라 전문가·기관 확인 전 추천 상태를 보류하는 항목

행동 관련 위험 신호를 단일 텍스트 추출값만으로 자동 영구 배제하지 않는다. 확인된 보호소 정책이나 사람이 검토한 evidence 없이 `aggression=true` 같은 모델 출력만으로 hard negative를 만들지 않는다.

### 7.3 Unknown과 conflicting

- `unknown`: 해당 정보가 입력되지 않았거나 관찰 기회가 없었음
- `not_applicable`: 해당 종·상황에 적용되지 않음
- `no`: 적절한 관찰 또는 명시 기록에서 부정이 확인됨
- `conditional`: 특정 조건에서만 가능하거나 추가 조치가 필요함
- `conflicting`: 출처 또는 시점에 따라 evidence가 충돌함

`unknown`, `not_applicable`, `no`를 하나의 false 값으로 저장하지 않는다. 충돌은 최신 evidence 하나로 덮어쓰지 않고 목록으로 유지하며 추천 화면에 맥락을 설명한다.

## 8. Feature Extraction 구조

### 8.1 목적

**[설계 결정]** extraction의 목적은 “동물의 진짜 성격을 판정”하는 것이 아니라, 자유서술에 **명시된 행동·생활조건 evidence를 정해진 schema로 옮기고 원문을 연결하는 것**이다.

### 8.2 후보 개발 흐름

```text
RescueGroups descriptionText / summary / qualities
                    +
일부 structured attributes
                    │
                    v
     target 후보별 데이터 적합성 검사
     - text-label overlap
     - class distribution
     - label 의미와 unknown 처리
     - 기관/종별 편향
                    │
                    v
       규칙 / 분류모델 / LLM 추출 비교
                    │
                    v
     value + evidence span + abstain/unknown
                    │
                    v
     영어권 내부 검증 + 한국어 PawInHand 수작업 검증
                    │
                    v
        채택된 feature만 Animal Profile에 반영
```

### 8.3 데이터별 연결

- RescueGroups structured fields는 잠재적 약지도 label 또는 비교 기준이다. 필드 존재만으로 ground truth로 간주하지 않는다.
- C-BARQ와 Shelter C-BARQ는 개 target의 이름·상황·경계를 정의하는 데 사용한다. factor score를 RescueGroups label로 직접 변환하지 않는다.
- Feline Behavior & Personality는 고양이 target을 별도로 정의하는 데 사용한다.
- Rehome Dogs는 compatibility와 경험자 필요 등의 필드가 실제 서비스 데이터에서 쓰이는 방식을 참고하되, false/unknown 전처리 문제 때문에 직접 정답으로 합치지 않는다.
- PawInHand 수작업 표본은 한국어 도메인 적용 성능과 원문 evidence 품질을 평가하는 핵심 검증셋 후보다.

### 8.4 추출 출력 정책

추출기는 `positive`, `negative`, `conditional`, `not_mentioned`, `ambiguous`를 구분할 수 있어야 한다. target마다 모델이 답하지 않는 abstention 경로를 둔다. 원문 span이 없는 생성형 값은 Profile에 넣지 않는 것을 기본으로 한다.

**[추가 검증]** 어떤 target을 실제 모델 출력으로 둘지, 규칙·분류모델·LLM 중 무엇을 사용할지, 다중 label 또는 ordinal label이 적절한지는 아직 결정하지 않는다.

추출 실험 결과는 feature별 implementation route에 반영한다. 자동화 성능이 충분한 feature는 `ML extraction` 또는 `LLM extraction`, 사람이 원문을 확인해야 안정적인 feature는 assisted extraction 또는 `verification-only`, 현재 근거로 사용할 수 없는 feature는 `unsupported`로 둔다. route 결정은 모델 종류가 아니라 독립 평가 성능, evidence 추적 가능성, 오류 비용을 기준으로 한다.

## 9. Recommendation 구조

### 9.1 단계별 흐름

1. **후보 생성**: 실제 입양 가능 상태, 종, 지역·이동범위 등 객관적 조건으로 후보를 만든다.
2. **Hard filtering**: 확인된 시스템·사용자·기관 hard violation만 제외한다.
3. **Feature-wise compatibility**: 각 feature의 의미와 척도에 맞는 compatibility function으로 확인된 관측값만 비교한다.
4. **Decision-family separation**: preference, care capacity, welfare requirement, household compatibility를 서로 다른 판단 축으로 계산한다.
5. **Non-compensatory check**: 확인된 hard violation이나 중대한 welfare requirement 충돌은 외형·나이 등 preference의 높은 점수로 상쇄하지 않는다.
6. **Evidence-aware calculation**: 결정에 사용된 feature의 coverage, 출처, 최신성, 충돌을 요약하고 unknown을 별도 상태로 유지한다.
7. **Uncertainty propagation**: 가능한 값의 범위가 정의된 unknown에는 score interval과 rank uncertainty를 계산한다. 근거 없는 범위는 만들지 않는다.
8. **Critical unknown detection**: 사용자별 중요도가 높고 상태 또는 순위를 바꿀 수 있는 unknown을 찾는다.
9. **State assignment**: `Ready`, `Needs information`, `Team review`, `Hold` 중 하나를 부여한다.
10. **Multi-criteria ranking and Top-K**: 상태와 비보상 조건을 먼저 적용하고, 같은 상태 안에서 여러 판단 축의 결과, evidence와 robustness를 이용해 순위화한다.
11. **Sensitivity/robustness check**: 합리적인 weight 범위와 unknown 시나리오에서 Top-K 및 후보 간 우열이 유지되는지 확인한다.
12. **Explanation and re-ranking**: 맞는 이유, 부족한 근거, 확인 질문, 원문 evidence를 보여주고 새 evidence가 들어오면 동일 파이프라인을 다시 실행한다.

### 9.2 점수 구조

한 개의 불투명한 총점 대신 최소한 다음을 분리한다.

- `preference_match`: 확인된 선호 일치도
- `care_capacity_match`: 사용자가 제공 가능한 돌봄과 요구의 일치도
- `welfare_requirement_status`: 충족·조건부·충돌·미확인
- `household_compatibility_status`: 아동·기존 동물·주거환경과의 공존 적합 상태
- `hard_constraint_status`: pass·fail·unknown/review
- `evidence_coverage`: 해당 사용자에게 중요한 feature 중 판단 가능한 비율
- `evidence_quality`: 출처·시점·관찰 맥락·검토 상태의 요약
- `critical_unknown_count`: 순위나 안전 판단에 중요한 미확인 항목 수
- `score_interval`: 관측된 evidence와 정당화 가능한 unknown 범위에서의 적합도 하한·상한
- `rank_uncertainty`: 후보의 가능한 순위 범위 또는 pairwise 우열의 불확실성
- `ranking_robustness`: 허용된 weight 변화와 evidence 시나리오에서 순위가 유지되는 정도

feature `j`의 비교는 단순 동일값 여부가 아니라 feature별 compatibility function으로 정의한다.

```text
c_j(u, a, e) -> [0, 1] 또는 {pass, conditional, conflict, unknown}
```

- nominal feature는 허용·비허용 조합표를 사용한다.
- ordinal/continuous feature는 차이, 허용구간, 방향성을 반영한 함수를 사용한다.
- care·welfare feature는 사용자가 제공할 수 있는 capacity와 동물의 최소 requirement를 비교한다.
- household compatibility는 동물 단독 특성이 아니라 해당 가구의 아동·기존 동물·환경과 함께 판정한다.
- source가 없거나 충돌하면 `unknown` 또는 `conflicting`을 반환하며 0, 중립값, 전체 평균으로 대체하지 않는다.

집계는 **lexicographic/threshold + within-state aggregation**의 비보상 구조를 기본으로 한다. hard constraint와 중대한 welfare·household conflict가 먼저 상태와 eligibility를 결정하고, preference 및 그 밖의 soft criterion은 같은 허용 상태 안에서만 가중 집계한다. 전체를 하나의 선형합으로 축소해 preference가 안전·복지 충돌을 보상하게 하지 않는다.

Multi-Criteria 단계에서는 네 판단 축을 각각 유지한 scorecard와 순위 근거를 제공한다. 가중치는 확인된 soft criterion에만 적용하며, 관측된 feature만으로 계산한 점수와 evidence sufficiency를 분리한다. unknown의 가능한 값 범위가 정책·척도상 정당화될 때는 낙관·비관 시나리오로 score interval과 가능한 rank range를 산출한다. 범위를 정할 근거가 없으면 숫자 구간을 가장하지 않고 `rank unresolved`로 표시한다.

weight sensitivity는 사전에 정한 합리적 weight 범위 또는 사용자 우선순위 변화에서 후보 간 순위 역전과 Top-K 유지율을 측정한다. 작은 변화로 순위가 뒤집히면 단일 순위보다 `near-tie`, 가능한 순위 범위, 결정에 중요한 criterion을 표시한다.

사용자에게 Match Score를 제공한다면 확인된 feature의 규칙·가중치에 따른 **상대적 적합도 표현**이어야 한다. 예를 들어 `87%`처럼 보이는 normalized score는 입양 성공확률, 장기 유지확률, 동물복지 달성확률을 뜻하지 않는다. 구현 단계에서는 등급, normalized score, 구간 중 어떤 표현이 오해를 줄이고 비교에 유용한지 평가한다. 어떤 표현을 선택해도 Evidence Coverage와 반드시 별도로 표시한다.

### 9.3 기술별 역할

| 기술 | 현재 역할 | 채택 조건 |
|---|---|---|
| 규칙 기반 filter | MVP 핵심 | 조건과 출처를 설명할 수 있어야 함 |
| Weighted content-based | MVP baseline | feature scale과 가중치의 근거·민감도 검토 |
| Constraint-based + Multi-Criteria | Final 추천의 주 구조 | hard/welfare 비보상 조건, 판단 축 분리, feature별 compatibility 검증 |
| Evidence/uncertainty-aware ranking | Final 추천의 주 구조 | unknown 비대체, score/rank uncertainty와 robustness를 설명 가능하게 산출 |
| Similarity | 탐색 보조 후보 | 유사함을 적합함으로 오해하지 않게 제한 |
| Semantic embedding | natural-language parsing·evidence retrieval·candidate retrieval 보조 | 최종 적합성이나 hard/welfare 판정을 embedding 유사도에 맡기지 않음 |
| LLM extraction | 텍스트 구조화 후보 | evidence span, abstention, 한국어 검증 성능 확보 |
| LLM explanation | 구조화 결과의 자연어화 후보 | 입력 사실만 사용하고 점수·판정을 변경하지 않음 |
| LLM reranking | MVP 제외, Final 실험 후보 | 동일 후보·정보에서 baseline 대비 이득과 제약 위반 0을 입증 |
| Agent | MVP 제외, workflow orchestration 후보 | 실제 검색·필터·근거조회·질문 도구가 있고 non-Agent 대비 성공률·비용 이득이 있을 때 |
| CF / A-LLMRec | 현재 부적합 | 충분한 반복 interaction과 시간순 평가가 생길 때 재검토 |
| RRS / stable matching | 개념 일부만 참고 | 다수 사용자 배정과 보호소 capacity가 실제 문제로 확인될 때 |
| 학습형 AFA / VOI | 현재 효과 주장 불가 | feature 값, target, 질문비용, 획득 성공률 확보 시 |
| MNAR/DR | 현재 직접 적용하지 않음 | 노출 로그와 propensity 또는 대표 평가자료 확보 시 |
| Learning-to-Rank | P2 연구 확장 | 독립적인 사람/전문가 ranking label 확보 시에만 검토. 자체 규칙으로 만든 synthetic ranking은 정답 label로 사용하지 않음 |

## 10. 불확실성 및 Evidence 설계

### 10.1 서로 다른 불확실성

1. **정보 결측**: 기록 자체가 없음
2. **관찰 기회 결측**: 해당 상황을 경험하지 않아 알 수 없음
3. **추출 불확실성**: 원문에서 구조화 값으로 옮기는 과정이 애매함
4. **측정 불확실성**: 평가자·상황·시점에 따라 행동이 달라질 수 있음
5. **출처 충돌**: 보호소·이전 보호자·Foster·Meet 기록이 다름
6. **도메인 전이 불확실성**: 영어권 RescueGroups에서 한국어 PawInHand로 적용할 때의 차이
7. **결과 불확실성**: 현재 적합도가 장기 유지·복지를 보장하지 않음

### 10.2 Evidence Coverage

단순 전체 필드 채움률이 아니라 사용자별 의사결정에 필요한 항목을 기준으로 계산한다.

```text
Evidence Coverage(u, a)
= 판단 가능한 중요 feature의 가중합
  / 사용자 u와 동물 a의 결정에 필요한 feature 가중합
```

가중치는 안전·공존·필수돌봄처럼 결정 영향이 큰 항목에 높게 둘 수 있으나, 초기 가중치는 **설계 가정**이다. 모델 성능처럼 해석하지 않고 sensitivity analysis 대상에 둔다.

### 10.3 상태와 사용자 출력

| 상태 | 의미 | 출력 |
|---|---|---|
| Ready | 확인된 hard violation이 없고 critical evidence가 최소 기준을 충족 | 추천 근거, 남은 일반 unknown |
| Needs information | 순위 또는 적합 판단을 바꿀 중요한 unknown이 있음 | 보호소 질문, 확인 순서, 답에 따른 영향 |
| Team review | 안전·기관정책·충돌 evidence 등 사람 검토가 필요 | 자동 결론 대신 담당자 확인 사유 |
| Hold | 확인된 hard violation 또는 필수조건 충돌 | 제외 이유와 근거. 변경 가능한 조건인지 구분 |

`Team review`는 캡스톤 팀이 행동·의료·입양 적격성을 전문가처럼 판정한다는 뜻이 아니다. 자동 시스템이 책임 있게 결론을 내릴 수 없어 **보호소 담당자, 관련 전문가 또는 권한 있는 사람의 확인이 필요한 상태**다. 실제 외부 담당자가 연결되지 않은 MVP 데모에서는 사용자에게 `담당자 확인 필요`로 표시하거나, workflow 검증을 위한 `simulated review state`로만 시연한다.

### 10.4 추가 확인 행동

질문만 제안하지 않고 가능한 evidence source를 구분한다.

1. 기존 기록 재조회
2. 보호소 직원 또는 이전 보호자에게 질문
3. 담당자가 허용한 구조화 관찰
4. Meet 또는 산책
5. 안전하고 운영 가능한 경우 Foster/home trial

각 행동은 비용, 소요시간, 안전성, 해당 feature를 실제로 관찰할 가능성이 다르다. 초기에는 규칙 기반 우선순위를 사용하고, 실제 운영 데이터 없이 최적 정보획득이라고 주장하지 않는다.

## 11. 평가 설계

실제 user–item interaction과 장기 적합성 ground truth가 없으므로 하나의 추천 정확도로 전체 시스템을 평가하지 않는다.

### 11.1 Feature extraction 평가

- 종별·target별 Precision, Recall, F1
- positive/negative/conditional/not-mentioned/ambiguous 혼동행렬
- evidence span 정확성 또는 사람 검토 일치율
- calibration 또는 confidence–error 관계
- abstention coverage와 수용 사례의 오류율
- 영어 RescueGroups 내부 검증과 한국어 PawInHand 외부검증을 분리
- 기관, 텍스트 길이, 종, 클래스별 성능 차이

### 11.2 Recommendation 평가

- 확인된 hard constraint 위반 동물의 Top-K 포함률. 목표는 0
- 전문가가 만든 가구–동물 시나리오에서 적격 후보 recall과 부적격 후보 노출
- soft weight 변화에 대한 순위 안정성
- evidence masking 전후 Top-K 유지율과 documentation bias 민감도
- 단순 규칙, weighted CBF, 추가 기법 간 동일 후보셋 비교

실제 선호 label이 없는 단계에서 NDCG·Hit@K를 장기 적합성 성능으로 보고하지 않는다.

### 11.3 Uncertainty handling 평가

- known negative와 unknown을 구분하는 정확도
- critical unknown 탐지의 전문가 합의율
- 위험하거나 정보가 부족한 시나리오에서 `Needs information`·`Team review` 발동률
- risk–coverage curve. 단, 보류 사례에도 독립 정답이 있는 경우에만 통계적 reject 성능으로 해석
- missing을 0/평균 처리한 baseline 대비 evidence masking robustness
- 필요한 정보 수 대비 순위 안정화 또는 판단 변경률

### 11.4 Explanation 평가

- 추천 이유가 실제 profile 값과 일치하는 faithfulness
- 근거 문장이 원문에 존재하는지
- 확인된 사실, 추출값, unknown, 가정을 사용자가 구분할 수 있는지
- 이해도, 과신, 의사결정 시간, 질문 유용성에 대한 사용자 평가
- 설명이 unsupported behavior를 생성하는 비율

### 11.5 Safety 평가

- 안전 관련 unknown을 안전으로 해석한 사례 수
- 모델 추출만으로 자동 제외한 사례 수와 사람 검토 결과
- 어린이·기존 동물·특별돌봄 시나리오의 필수 경고 누락률
- 충돌 evidence를 숨기거나 최신값 하나로 덮어쓴 사례 수
- 품종을 행동 대리변수로 사용한 경로가 없는지 감사

### 11.6 향후 운영·outcome 평가

실서비스 또는 협력기관 데이터가 생기면 다음을 분리한다.

- 탐색: 노출, 클릭, 저장, 문의, 방문
- 선택: 신청, 담당자 승인, 입양 완료
- 초기 적응: 1주·1개월 행동, 기대–경험 차이, 지원 요청
- 장기: 유지, 반환·재양도, 만족, 동물복지
- 운영: 상담 부담, 정보획득 비용, 보호소 체류, 동물 관찰 부담

입양 완료를 “좋은 매칭” label로 사용하지 않는다. 반환 부재도 만족이나 동물복지와 동일하지 않다.

## 12. MVP와 Final 범위

### 12.1 MVP

MVP는 이후 모든 고도화의 비교 기준이 되는, 반드시 동작하고 재현 가능한 baseline system이다. 아래 범위를 유지하되 각 feature의 implementation route에 따라 자동화 수준을 조정한다. 질문·관찰 기능은 기본 확인 필요 표시와 evidence update를 뜻하며, 질문 우선순위의 자동 결정은 포함하지 않는다.

1. 국가 API·PawInHand 기반 실제 후보 catalog
2. 최소 User Profile과 hard/soft 구분
3. canonical schema를 유지한 Base Animal Profile과 MVP operational route
4. 원문 evidence를 보존하는 제한된 feature extraction
5. 확인된 hard violation 기반 filtering
6. 설명 가능한 weighted CBF baseline
7. Match와 Evidence Coverage 분리
8. Critical Unknown 탐지
9. 보호소 질문·관찰 체크리스트
10. 새 evidence 입력 후 재추천
11. `Ready / Needs information / Team review / Hold` 상태

MVP의 확인 흐름은 `Unknown 탐지 → 추가 확인 필요 표시 → 새 evidence 입력 → 동일 pipeline 재실행`이다. 보호소 질문·관찰 체크리스트는 제공하지만 여러 unknown의 우선순위를 decision sensitivity로 자동 선택하는 기능은 Final/P1 범위다.

MVP에서 제외한다.

- collaborative filtering과 A-LLMRec
- stable matching과 전체 배정 최적화
- RL Agent
- 장기 성공확률·반환확률 예측
- 품종 기반 성격 보간
- 학습형 AFA·통계적 reject의 효과 주장
- Austin outcome을 추천 정답으로 사용
- 병원·약국·미용 정보를 compatibility score에 직접 반영

### 12.2 Final 후보

Final은 AI-assisted implementation을 활용해 일정 안에서 구현 가능한 기능을 적극 확장한 목표 시스템이다. 다만 기능이 복잡하거나 AI를 사용했다는 사실이 아니라, MVP baseline 대비 개선 또는 독립적인 역할을 검증할 수 있는 기능만 추가한다.

- 종별로 검증된 multiple behavioral / compatibility feature extraction
- rule-based decision sensitivity를 이용한 dynamic questioning
- 새 evidence 입력에 따른 profile update와 재추천
- evidence 출처·충돌·시점 UI
- documentation bias robustness 개선
- feature-wise compatibility와 preference/care/welfare/household 축을 분리한 multi-criteria ranking
- hard·welfare 조건의 non-compensatory 처리
- 가능한 경우 score interval, rank uncertainty, weight sensitivity와 ranking robustness 표시
- 구조화된 결과만 사용하는 LLM 기반 explanation과 사용자 이해도 실험
- LLM extraction과 rule/classifier 등 non-LLM baseline 비교
- PawInHand 한국어 외부검증
- 가능한 경우 Agent workflow와 deterministic/non-Agent workflow 비교
- 장기 scenario stress test. 단, 확률 예측이 아니라 조건 변화 시 충돌 항목을 재계산

Final은 기능 수가 아니라 **MVP baseline보다 무엇이 개선됐는지 검증 가능한 범위**로 정의한다. Agent나 LLM을 사용했다는 사실 자체는 성과나 채택 근거가 아니다.

## 14. 설계를 확정하기 위해 다음에 필요한 데이터 분석

이 항목은 다음 단계의 분석 목록이다. 이번 문서 작성 단계에서는 실행하지 않았다.

### 14.1 RescueGroups description–target overlap 분석

**목적:** `activity_level`, `energy_level`, `exercise_need`, `isDogsOk`, `isCatsOk`, `isKidsOk`, `isHousetrained`, `newPeopleReaction`, `ownerExperience`를 최종 Animal Profile과 feature extraction target으로 사용할 수 있는지 판단한다.

확인할 내용:

- target이 비결측인 개체 중 descriptionText도 존재하는 비율
- target별 클래스 분포와 소수 클래스 수
- text에 target 근거가 명시된 비율과 structured 값의 일치 여부
- 종별·기관별 분포 차이
- 동일 문구·템플릿 중복으로 인한 train/test leakage 위험

### 14.2 RescueGroups label semantics 검증

**목적:** structured field가 실제 행동 관찰, 기관 정책, 기본값, 미입력의 대체값 중 무엇을 의미하는지 확인해 false와 unknown의 혼합을 막는다.

확인할 내용:

- 필드별 API 정의와 실제 값 패턴
- non-null 값의 dominant class가 높은 이유
- `false`가 명시적 부적합인지 기본값인지
- related reason/detail 필드와의 논리 일치

### 14.3 PawInHand attribute coverage와 한국어 evidence audit

**목적:** 해외에서 정의한 schema 중 실제 한국 추천에 사용할 수 있는 feature와 현장 확인으로만 남겨야 할 feature를 구분한다.

확인할 내용:

- 종별 attribute evidence coverage
- positive/negative/conditional/unknown 분포
- 보호소·텍스트 길이별 기록편차
- 원문으로 판정 가능한 최소 target 집합

### 14.4 국가 API–PawInHand identity resolution audit

**목적:** 객관적 기본정보와 PawInHand 상세서술을 안전하게 결합할 수 있는지, 최종 catalog의 중복·오매칭 위험이 어느 정도인지 판단한다.

확인할 내용:

- 연결 key별 match rate와 충돌 유형
- 1:1, 1:N, N:1 사례
- 갱신 시점 차이와 상태 불일치
- 연결 실패 시 fallback profile 정책

### 14.5 종별 Operational Animal Profile routing 확정

**목적:** canonical schema를 단순 축소하는 것이 아니라 실제 관찰 가능성, 데이터 근거, 추출 성능, 안전상 중요도를 바탕으로 각 feature의 implementation route와 MVP/Final 사용범위를 확정한다.

방법:

- feature별 문헌 중요도, 한국 coverage, RescueGroups 학습 후보 수, 안전 영향, 사용자 질문 가능성을 한 표에서 비교
- 공통·dog-specific·cat-specific canonical schema를 유지하면서 종별 operational route를 부여
- `direct`, `ML extraction`, `LLM extraction`, `verification-only`, `unsupported`로 분류
- 각 feature의 recommendation role과 `MVP / Final` 사용범위를 명시

산출물:

| feature | species | implementation route | recommendation role | scope |
|---|---|---|---|---|
| canonical feature | dog/cat/common | direct / ML / LLM / verification-only / unsupported | filter / score / evidence / verification | MVP / Final |

### 14.6 Hard / Soft / Verification 시나리오 검토

**목적:** unknown을 부적합으로 처리하지 않으면서도 안전상 필요한 보류를 놓치지 않는 정책을 확정한다.

방법:

- 어린이, 기존 개, 기존 고양이, 장시간 외출, 초보 보호자, 특별돌봄 등 가상 가구 시나리오 작성
- 프로젝트 팀·보호소 실무자·행동 전문가가 조건 분류와 예외를 검토
- false exclusion과 unsafe inclusion을 별도로 기록

### 14.7 Evidence Coverage와 ranking robustness 분석

**목적:** 기록이 자세한 동물이 더 적합한 동물처럼 노출되는 documentation bias를 방지하고, Match와 Evidence를 분리한 설계가 실제로 순위를 안정시키는지 확인한다.

방법:

- 동일 동물의 evidence를 단계적으로 masking
- missing=0, missing=평균, unknown 분리 방식을 비교
- soft weight와 criterion threshold를 사전 범위 안에서 변화
- score interval coverage, 가능한 rank range, pairwise 순위 역전, Top-K 유지율, 보호소별 노출 분포, critical unknown 탐지 변화를 측정

### 14.8 한국어 feature extraction 검증셋 설계

**목적:** RescueGroups에서 개발한 추출기가 PawInHand의 한국어·보호소 문체에서도 유효한지 검증할 수 있는 독립 기준을 만든다.

방법:

- 개/고양이, 보호소, 텍스트 길이, rule hit/no-hit, 희귀 target을 포함한 층화표본
- 명시 evidence 유무, polarity, conditional, ambiguous, evidence span을 이중 라벨링
- 불일치 조정과 annotation guideline 작성

### 14.9 User Profile 최소 질문 실험 설계

**목적:** 질문 수를 늘리는 것이 아니라 hard filtering, soft ranking, critical unknown 탐지에 실제 필요한 최소 사용자 정보를 정한다.

방법:

- 질문별로 제거했을 때 후보군·순위·verification 항목이 얼마나 변하는지 비교
- 사용자가 답하기 어려운 질문과 시간 측정
- 초기 필수 질문과 후보별 추가 질문으로 분리

### 14.10 평가 gold set과 baseline 고정

**목적:** user–item interaction ground truth가 없는 상태에서도 extraction, recommendation, uncertainty, explanation, safety를 재현 가능하게 비교한다.

방법:

- 전문가 검토 가구–동물 시나리오와 명시적 판정 근거 작성
- 규칙 filter + weighted CBF + unknown 분리를 고정 baseline으로 정의
- 각 평가 층의 metric, split, 누수 방지 규칙, 실패 사례 기록 형식을 사전 등록
